## Method

- Each run is a fresh subprocess. Stages: `preprocess` = `read_yaml`; `build` =
  `Model.build`; `solve` = `Model.solve` minus `postprocess`; `postprocess` = time in
  `BackendModel.load_results` (variables, global expressions, postprocessed math);
  `write` = `to_netcdf`. Peak RSS per stage comes from a 5 ms sampler of
  `/proc/self/statm`; the last column is the peak observed from outside.
- Variants: `main` and `speedups` use `build.backend: highs`. `pyomo` builds with the
  Pyomo backend, writes the LP (`lp_write`) and solves that file with highspy:
  Pyomo's own HiGHS interfaces do not work on Calliope's `pyomo.kernel` model (see
  BUGS.md), so `pyomo` has no results loading and no NetCDF write. For operate and
  SPORES the `pyomo` rows only cover the first build and are not comparable.
- Synthetic models (`bench/synthetic.py`): N/5 copies of the 5-node national_scale
  system, the `region1` hubs joined in a ring, time series scaled per copy. Links are
  techs in Calliope, so `techs` grows with N (54 at 50 nodes, 254 at 250 nodes).
- Caps: 20 min and 28 GB RSS per run. Single-thread HiGHS needed 104 s for 50×168
  already, so synthetic sizes above 5×8760 nodes·hours, and all 250-node sizes, are
  run **build only** (`ok-build-only`). 250×2190 exceeded 28 GB during build in all
  three variants, so 250×8760 was skipped. Not run: 250×2190 and 250×8760 at all; the
  solve of 50×2190, 50×8760, 250×168.
- Another agent was compiling Rust on the same VM at times; single runs, no
  repetitions. Treat differences below ~10% as noise.

## Key findings

1. **Solve dominates where the LP is hard; build dominates as the model grows.**
   national_scale 8760 h: build 13%, solve 85% (239 s single-thread HiGHS). urban
   8760 h: build 49%, solve 45%. At 50 nodes × 8760 h the build alone takes 709 s and
   10.6 GB; at 250 nodes × 168 h, 195 s and 4.1 GB; 250 × 2190 does not fit in 28 GB.
2. **Build cost and memory grow with the dense nodes × techs × timesteps product.**
   From 5×8760 to 50×8760 the nodes × techs product grows 67× (links are techs);
   build time and build RSS both grow about 20×. Since
   techs grow with nodes, dense arrays grow quadratically in nodes: 250×2190 does not
   build in 28 GB. This is the strongest argument for sparse/long storage in the
   Phase 2 spike.
3. **`feat/highs-speedups`** cuts the build by 18–36% (national 36→23 s, urban 61→40 s,
   50×2190 146→106 s, 50×8760 709→573 s), with no change in peak RSS, solve or
   postprocess. The Pyomo backend builds about as fast as `speedups` (and faster at
   50×8760: 505 s) but needs 40–50% more memory, plus LP writing (14–21 s at 8760 h).
4. **Operate mode is dominated by Python, not HiGHS.** national_scale, 31 days, 12 h
   window / 24 h horizon: 62 windows; HiGHS itself takes ~5 ms per window, but each
   window costs ~1.0 s of `update_input` (181 calls, 61 s total: `storage_initial`,
   `sink_use_equals`, `source_use_max`, each rebuilding all referencing components) and
   0.8 s of `load_results` (50 s total). Build + update + results are >95% of the
   119 s. In-place updates and vectorised results extraction are where a port gains most.
5. **SPORES** (national_scale, 31 days, 3 SPORES): 4 solves, 9.5 s each on average
   (HiGHS), `update_input` 0.8 s total, results 4.7 s; solve share 73%.
6. Peak RSS of a solved run is reached in `solve`/`postprocess`, not in build:
   national 8760 h peaks at 1.1 GB vs 0.54 GB after build (HiGHS model + results).

### Realistic ceiling for a Rust port (Amdahl, same HiGHS)

| model | build+pre+post+write share (main) | end-to-end ceiling if those went to 0 |
|---|---|---|
| national 8760 h | 15% | 1.2× |
| urban 8760 h | 55% | 2.2× |
| 5 nodes × 2190 h | 48% | 1.9× |
| operate, 31 d | >95% (HiGHS ~0.3 s of 119 s) | >10× |
| 50 nodes × 8760 h | build alone 709 s, 10.6 GB | build-bound; memory decides feasibility |
